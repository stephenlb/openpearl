OpenPearl is open source on GitHub. It reads a ticket, implements it, opens a PR, reviews it in a loop and auto-merges. All as a GitHub workflow. If it isn't confident, it hands the PR to a human. Seamlessly integrates into your existing CI/CD.

The story

A pipeline that maintains itself

Software delivery pipelines can now be implemented and be self-maintained. We built OpenPearl with an initial prompt that generated a workflow intended to be self-modifiable. Once the boilerplate scaffolding was set, we began using the engine itself to modify and expand its capabilities. It took a few tries, with a few false starts where the engine couldn't modify itself successfully. We're only talking about YAML files because this is a GitHub workflow; there are no other files involved except for evals.

Once we got past the initial problems, we added features that let the workflow integrate seamlessly with Jira, Trello, and GitHub issues. We added image support so the models have vision. Then we added a continuous chat session in issues and pull requests. It became obvious that we needed an eval to decide when a human should verify and validate a pull request, and when the ticket can be auto-merged. The goal is for most tickets to merge automatically. For safety, any modification to the workflows typically triggers human review.

The preferred workflow

We also wanted a command-line interface, so you can submit new tickets directly from your terminal or have an AI agent trigger a series of new tickets that the OpenPearl pipeline implements automatically. This has become the preferred method: spin up your Codex or Claude Code instance and use the GitHub CLI (gh) to create new issues. Ask your coding assistant to create issues for complex tasks, and it may split the work across several tickets.

How we started

At PubNub and Blocks.AI, we wanted to innovate our engineering workflows. Early in 2024, we realized it might be possible to build a software delivery pipeline from Jira tickets to merged PRs. We tried and failed. Most models and harnesses were newly emerging, and even simple tickets needed a lot of back and forth between the harness and a human. Now the models and harnesses are good enough that the automation pipeline we tried to build in 2024 is readily available in 2026.

The simple workflow loop

This is what OpenPearl is: a simple YAML file that describes a workflow for GitHub Actions. It fetches tickets from Trello, Jira, and GitHub Issues, then opens a branch, modifies the code, pushes the branch to origin, and opens a PR. It evaluates the code review in a loop until it looks clean, and finally runs an eval to determine whether the PR can be merged automatically or needs a human. That is the simple loop.

Why workflows

Why not a pile of markdown files?

Instead of piling instructions into markdown files (CLAUDE.md, AGENTS.md, rules and memory docs) that get loaded into the agent's context on every run, OpenPearl uses workflow orchestration and evals. The workflow drives each step (implement, review, fix, merge) as a separate, focused agent call, and evals decide whether a PR is ready to merge. Context isn't consumed by standing instructions, so the agent keeps its context for the actual task.

How it works

How the night shift works

When an owner, member, or collaborator opens an issue, .github/workflows/issue-to-pr.yml runs:

  1. The agent implements the issue and opens a PR.
  2. The agent CLI runs two review/fix rounds.
  3. The agent CLI runs the eval in .github/workflows/evals/pr-ready-to-merge.md. On YES the PR is squash-merged; otherwise it stays open for a human.

Usage

Drop tickets in the slot (gh)

Install the GitHub CLI and run gh auth login once.

gh issue create   # interactive: prompts for title and body
gh issue create -t "Add dark mode toggle" -b "Add a toggle to the settings page."
gh issue list
gh issue view 123 -c
gh issue comment 123 -b "Also handle the empty state."
gh issue close 123
gh pr list
gh run watch

To attach an image, commit it with gh api and link it (replace {owner}/{repo} in the body with your repo):

gh api -X PUT repos/{owner}/{repo}/contents/issue-assets/shot.png \
  -f message="Add shot.png" -f content="$(base64 < shot.png | tr -d '\n')"
gh issue create -t "Button is misaligned" \
  -b "![shot](https://github.com/{owner}/{repo}/blob/HEAD/issue-assets/shot.png?raw=true)"

Setup

Move the robot in

Paste this prompt into your coding agent (Claude Code, Codex, OpenCode, Pi) from the root of your project. It installs the OpenPearl workflow files.

Install OpenPearl into this project.

1. Download the .github/workflows directory from https://github.com/stephenlb/openpearl (branch main) into this project's .github/workflows directory: issue-to-pr.yml and the evals/ folder (evals/pr-ready-to-merge.md). Only also copy jira-to-issue.yml, issue-comment-to-jira.yml and trello-to-issue.yml if I use Jira or Trello. For example: git clone --depth 1 https://github.com/stephenlb/openpearl /tmp/openpearl, then copy the files. Do not overwrite existing files without asking me.
2. Do not modify any other files in my project.
3. Commit the new files on a branch and tell me to finish setup:
   - Enable Settings > Actions > General > "Allow GitHub Actions to create and approve pull requests".
   - Add the secret ANTHROPIC_API_KEY under Settings > Secrets and variables > Actions (or the Amazon Bedrock secrets listed in https://github.com/stephenlb/openpearl#setup).
